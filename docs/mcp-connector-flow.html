Authorization Server vs Resource Server

    

      Poora confusion isi line pe hota hai. Ek token banata hai, doosra token
      check karta hai. Trace me dekho — steps 6–14 sirf AS ke saath hain,
      steps 15–26 sirf RS ke saath.
    

    

      

        
Authorization Server

        
auth.blue-node.dev · token banata hai

        
    
          
  • /.well-known/oauth-authorization-server — endpoint discovery (RFC 8414)
    • 
          
  • /authorize — user login + consent screen, auth code deta hai
    • 
          
  • /token — code + PKCE verifier → access + refresh token
    • 
          
  • /register — Dynamic Client Registration, Claude khud register hota hai (RFC 7591)
    • 
          
  • /.well-known/jwks.json — public keys, taaki RS signature verify kar sake
    • 
          
  • Owns: user identity, consent records, client registry, token signing keys, scope catalog
    • 
        

      

      

        
Resource Server

        
api.blue-node.dev/mcp · data deta hai

        
    
          
  • /mcp — asli MCP endpoint: tools, resources, prompts
    • 
          
  • /.well-known/oauth-protected-resource — "mera AS ye hai" (RFC 9728)
    • 
          
  • Har request pe: signature, iss, aud, exp, scopes validate
    • 
          
  • Token nahi/galat → 401 + WWW-Authenticate header
    • 
          
  • User login — nahi karta
    • 
          
  • Consent screen — nahi dikhata
    • 
          
  • Token issue — kabhi nahi
    • 
        

      

    

    

      Dono ek hi host pe bhi ho sakte hain — tab authorization_servers apne aap ko
      point karta hai. blue-node abhi apne frontend ke liye dono kaam kar raha hai
      (login token deta hai + middleware verify karta hai). Lekin Claude
      third-party client hai — usko browser redirect, consent screen aur DCR
      chahiye, jo aaj nahi hai. Isliye RS-only se start karna sasta padta hai.
    

  


  

    
Jahan log phaste hain

    
Ye saat cheezein trace me marked hain — build karte waqt in pe rukna.

    

      

        
1 · aud check chhod dena

        
Sabse common bug. Kisi doosre server ke liye bana valid token aapke server pe chal jaayega — "confused deputy". resource param (RFC 8707) isi liye hai.

      

      

        
2 · Token passthrough

        
MCP spec me explicitly mana hai — upstream ka token aage forward karna, ya doosre audience ka token accept karna. Har hop apna token.

      

      

        
3 · Consent skip karna

        
Third-party client hai. User ko dikhna chahiye kaunse scopes diye jaa rahe hain. Silent grant = security bug, feature nahi.

      

      

        
4 · Tool description ko doc samajhna

        
Wo prompt hai. Model usi se decide karta hai. "Kab call karna hai" likho — sirf "kya karta hai" likhne se tool trigger hi nahi hoga.

      

      

        
5 · Arguments ko trust karna

        
arguments model ka output hai — untrusted. Zod parse + per-tool scope check + tenant filter. Auth ≠ authz.

      

      

        
6 · Bada tool result

        
Result seedha model ke context me jaata hai. 500 rows bhejna context jalana hai. Paginate karo, summary do, cursor rakho.

      

      

        
7 · Ek hi mcp scope

        
Sab tools ek scope ke peeche = all-or-nothing. Per-tool scopes do (leads.read vs leads.write) taaki user read-only de sake.
